## 额外事实错误与边界

A/Q045、A/Q060和A/Q093为主要事实串线或未来外推，A/Q100还把“审计系统由合规维护组负责”扩张为“独立标记由该组管理”。B/Q021先写“缓存由赤霄缓存集群维护”，把实例当作维护主体，后半句团队正确不能消除错误关系；B/Q100也把系统职责扩张成标记或功能管理职责。B/Q093的实例→整个系统职责扩张同样没有依据。这些错误都保留在JSON。

D/Q024主要关系链正确，仍额外写“在2025年之前，赤霄由旧运维组维护”。原文只明确2024年职责及2025年终止，不能证明整个2025年之前区间。审核保守记为一项轻微时间范围扩张；它使D严格内容成功为17/18。修正应写“2024年由旧运维组维护，该职责于2025年终止”，或直接删掉无关历史说明。

C/D对Q093均保留2027未知，没有把2026团队外推；但仍罗列赤霄历史或其他缓存团队，这些事实没有帮助回答支付系统未来安排，建议删减。Q069四组均正确保留备份与步骤顺序，没有因短名触发错误流程。

## 引用检查

A/B使用旧式纯文本工具上下文，模型没有实际文件名或E编号。部分回答仅引用正文标题，另一些自行把中文标题拼成 `.pdf` 或编造E编号。A/Q100甚至给“缓存职责登记.pdf，E2”，实际唯一来源为 `other_kb.pdf`，工具没有E2；B/Q100写E381，亦不存在。标题看起来相似不等于可核对的实际文件来源。

C/D带结构化证据，17个带事实回答均出现至少一组真实文件与E编号。这个改善同时包含上下文元数据包装，不能全部称为检索准确率提高。

引用存在还不够。C/Q021和D/Q021只引 `order_ownership.pdf` 来支持“订单系统所用缓存由甲组维护”，缺少证明订单使用赤霄的 `order_architecture.docx`；D/Q041维护结论同样缺少架构来源。D/Q024历史句虽引用了真实history.pdf，原文不支持被泛化的全部时间区间。完整引用覆盖因此为C16/17、D14/17，不能把“出现E编号”当作引用100%合格。
