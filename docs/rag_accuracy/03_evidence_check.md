# 第三阶段：证据覆盖检查与一次补检

工程实现日期：2026-10-22。按用户继续下一步的要求推进工程和隔离实验；前两阶段 Gold 的人工审核状态仍为 `pending_human_review`，未替代人工审阅，也未宣称正式效果 Gate 通过。

## 实际链路

仍只通过 `search_knowledge_base` 调用检索服务，Agent 的知识库工具上限保持一次。现有 Milvus 混合检索、父块取回、Reranker、可选图谱和路径配额先照常执行。

开启证据检查后：

1. 从请求 trace 的原始用户问题识别最多三个目标：实例名称、维护关系、有效期、故障、处理步骤、前置条件，防止 Agent 工具查询改写漏掉要求。直接调用服务时使用传入问题。原问题及限定完整保留；超过三项的剩余要求标为未确认。
2. 对首轮 Top K 的原文作保守规则检查。维护关系需有系统→实例及实例→团队的完整来源；处理步骤需明确绑定到该实例。同一实例的其他故障流程不算支持。
3. 已完整支持时不补检；发现可识别目标缺失时，把原问题、缺失目标和已明确关联的实例组成一个查询，在同一用户和知识库范围内补检一次。
4. 补检使用现有文本检索，关闭该次图扩展及单独重排；最多取回三个父块，与首轮 Top K 合并后做一次重排。按完整的已验证证据组保留必要来源，最终仍不超过原 Top K。
5. 补检没有增加明确支持时，保持首轮选择，避免相似但无关的手册挤掉原证据。最终重新检查实际选中的文本，输出编号引文与覆盖状态。

补检不会递归触发证据检查或图扩展。四组使用相同的首轮候选预算，C/D 增加的至多三个父块是本次待评测变量，不能称为零额外检索成本。查询范围继续由底层 SQL/Milvus 过滤，结果匹配再核对用户、知识库、父块及文件哈希。真实用户知识库没有被实验导入或回填。

## 支持与限制

首版使用确定性规则，不调用分解或校验 LLM，不读取评测 Gold。它面向具有明确中文表达的运维与实例关系文档，不是通用自然语言蕴含系统。

所有 `supported` 项保留连续原文引用与复合来源键，表示找到了受限规则能确认的局部事实。仅文本相似不算支持。未识别的问题类型、时间/版本限定保守标为 `partial`，不会为这些情况盲目反复搜索。复杂比较、别名消歧、无明确实体的指代追问、任意时态及不同文档句式仍需后续评测扩展。

覆盖状态为 `supported / partial / missing / conflicting`。同一主体的同类事实出现不同值时保留冲突，不使用多数投票。步骤必须具有完整句子结束标记；同一父块出现不同故障时，不猜测流程属于哪一种故障。当上下文预算不足时丢弃整个父块并重新评估，不截断流程后继续声称完整支持；发现过冲突也不会因去掉一方而变成确定答案。

工具文本通过 JSON 引用文档及文件名，明确将引文内指令视为不可信数据；缺失项须说明缺乏依据，冲突项须说明来源分歧。最终回答只引用文件名和证据编号，不输出内部父块 ID。原默认/指定知识库系统提示词没有重写，指定库约束继续生效。此机制是生成约束，不是对模型最终服从性的保证；真实回答须单独检查。

## 默认预算

| 配置 | 默认 | 允许范围 |
| --- | ---: | ---: |
| `EVIDENCE_CHECK_ENABLED` | false | 全局默认，可被用户设置显式覆盖 |
| `EVIDENCE_MAX_RETRIEVAL_ROUNDS` | 1 | 0–1 |
| `EVIDENCE_EXTRA_PARENT_LIMIT` | 3 | 1–3 |
| `EVIDENCE_CHECK_TIMEOUT_MS` | 800 | 1–5000 |
| `EVIDENCE_RETRIEVAL_TIMEOUT_MS` | 10000 | 1–30000 |
| `EVIDENCE_TOTAL_TIMEOUT_MS` | 12000 | 1–60000 |
| `EVIDENCE_MAX_CONTEXT_CHARS` | 12000 | 2000–40000 |

总预算仅覆盖首轮之后的扩展；补检预算不允许扩大首轮 Top K。当前字符预算是可执行的近似上限，不等同于模型 Token 数；各组实验仍固定 K 和同一字符预算。超时是协作式取消边界；同步 SDK/事件循环受阻时，实际墙钟可能超过设定值，不能把配置值当成严格 SLA。

本机诊断发现，原重排函数每次创建 HTTP 客户端会重复加载证书，模拟 HTTP 响应、完全不联网时三次调用仍各耗时约 2.8–3.0 秒。对照排除了网络和数据库：复用同一个仍启用证书验证的 SSL 上下文后，客户端初始化降至毫秒级。因此仅复用 HTTPX 原策略创建的证书上下文，并把首次初始化移到线程；请求模型、文档、Top N、三秒 HTTP 超时、三次重试及 TLS 验证不变。未缓存重排响应，也未复用跨事件循环的 HTTP 客户端。最终四组共同使用这个修正，先前存在本地阻塞的实验单独保留，不能拿其延迟与最终实验直接比较。

检查异常、配置越界、补检异常或超时均回退到首轮图谱/向量结果，并保留失败类型和已发生的补检次数。取消继续向上传播，避免后台多余调用。关闭检查时保留原工具字符串格式和原检索选择。

## 设置与观测

「设置 → RAG 设置 → 证据完整性检查（实验）」支持跟随服务默认、开启或关闭。侧栏摘要显示实际选择的开关状态。偏好存入已有用户配置 JSON，默认补字段，无需新建表或改动画像版本。

检索 trace 记录首轮/最终覆盖、支持引文与来源、补检次数、额外候选数、最终新增父块数及各阶段耗时。首轮与补检的父块仍进入受控评测快照；只有最终实际发送的上下文标记为 `final`，不会把补检中间结果重复计作模型证据。生产日志仅包含计数、耗时、匿名请求 ID 和异常类，不输出问题、引文或凭据。

## 复现实验

沿用原 100 题、原语料映射和 Gold，运行 A 无图无检查、B 图谱、C 检查、D 图谱加检查四组。每组都实际调用 embedding/重排，没有用旧录制响应冒充新实验；检查器本身不调用 LLM。实验参数、源码和评测脚本指纹均保存，各组指纹或 Gold 不一致时拒绝比较。

```powershell
.\.venv\Scripts\python.exe -m evaluation.ablation --output-dir .runtime/rag_accuracy/phase3/new_run
.\.venv\Scripts\python.exe -m evaluation.ablation --output-dir .runtime/rag_accuracy/phase3/new_run --concurrency 1 --execute
```

默认 dry-run；输出目录必须不存在，保留失败运行且不覆盖。可显式选择并发数 1–4；较高并发会影响图查询和远端重排延迟，不应把降级题当作成功算法收益。

真实 Agent 验证：

```powershell
.\.venv\Scripts\python.exe -m evaluation.answer_eval --mode vector_plus_graph_plus_check --max-cases 2 --execute --output .runtime/rag_accuracy/phase3/new_qa.jsonl
```

Agent 实验使用独立 Redis 会话、隔离知识库，关闭画像和长期记忆，不保存实验对话到真实用户原始消息表。
