# EchoMind：多会话与前端设计补充

版本：v0.2，目标设计与实施对照。日期：2026-10-26。

本文件补充 [上下文管理与状态编排计划](EchoMind_ReAct_Context_State_Loop_Engineering_Design.md)。新增需求来自用户：同一知识库支持多个会话窗口，后续前端参考 Codex 风格，同时保持首页简洁。下文保留目标设计；首版已实现范围和验证结果见 [交付记录](multi_conversation_delivery.md)，其余能力仍为后续设计。

## 1. 当前问题与目标

实施前的源码基线（当前差异见交付记录）：

- `frontend/app.py` 已通过 `chat_session_id` 区分会话；“新对话”创建新 ID，并更新 `?session=...` 链接。
- 后端 `backend/agent.py` 按 `user_id:session_id` 使用 checkpoint，因此具备区分多个会话的基础。
- 页面只管理当前聊天，没有知识库下的会话列表、命名、搜索、归档和再次打开入口。旧会话主要依赖原链接访问。
- `select_knowledge_base()` 只更换当前知识库，没有同步切换会话；同一会话可能已有不同库的历史。
- `/runs` 按已知 session 查询运行记录，不提供用户的会话目录。页面恢复历史展示，也不等于模型 checkpoint 已恢复。

目标是“一个知识范围，多条独立会话，每条会话有稳定身份和可恢复历史”。先支持侧栏切换和浏览器多标签页；应用内多标签或分屏作为后续增强，避免第一版挤占聊天区域。

## 2. 对象与隔离边界

| 对象 | 责任与规则 |
|---|---|
| 用户 | 所有会话操作使用服务端认证身份；链接和客户端 user_id 都不能授予访问权限 |
| 知识范围 scope | 单个知识库，或当前产品的“默认知识库”聚合范围；聚合范围不是独立实体知识库 |
| conversation | 独立聊天：稳定 ID、标题、所属范围、创建/更新时间、归档状态、revision |
| turn | 一次用户发送和相应回答；持有 client_turn_id、顺序、终态和上下文来源 |
| run | 一次具体执行与审计；不能用 run_id 代替 conversation_id |
| checkpoint | 特定 conversation 和 schema/scope epoch 的执行缓存；过期不删除会话目录和持久消息 |

建议业务关系为：用户 → 知识范围 → 多条 conversation → 多个 turn → 对应 run。新建 conversation 使用 UUID；现有 session_id 作为兼容映射保留，不直接改写旧主键。

新会话创建时绑定 scope，发送时由服务端读取并校验，不接受客户端任意改库。要换库，导航到目标库下的会话或新建会话；跨库比较在明确选择的聚合范围中新建会话。旧库的 ToolMessage 不跟随导航进入新会话。

“默认知识库”保持现有搜索全部授权知识库的产品含义。conversation 保存聚合范围策略，每个 turn 保存当时解析出的授权库集合/版本用于审计；下一轮重新核对权限，不把旧集合视为永久授权。文档更新、库新增或权限变化都需重新核对证据。

不同会话默认不读取彼此的消息和摘要。现有用户级长期记忆可能跨会话检索，应明确标注来源并遵循用户开关；它不是会话隔离失效，也不能静默复制另一会话全文。画像和技能仍按本轮可信设置注入。

## 3. 用户操作约定

| 操作 | 预期行为 |
|---|---|
| 在知识库 A 中新建对话 | 创建 A 下的独立 conversation，不清除原会话；未发送的空白页可先作为本地草稿，首次发送再幂等创建 |
| A 中有多个会话 | 可从侧栏切换；每个会话保留自己的消息、草稿、执行状态和分页位置 |
| 从 A 切到 B | 打开本浏览器记住的 B 最近会话，或显示 B 的空白页；不复用 A 的会话 ID |
| 通过历史链接打开会话 | 先检查权限，按会话绑定范围选中知识空间，再加载消息；不由浏览器残留的 KB 选择覆盖范围 |
| 刷新或重新打开 | 从服务端读取会话和消息；checkpoint 过期时按上下文策略重建，并记录重建原因 |
| 新标签页打开 | 链接定位同一 conversation；在另一个新会话提问则使用另一 ID |
| 重命名 | 默认从首条问题确定性截取短标题，可手动修改；第一版无需额外模型调用 |
| 归档/恢复 | 归档后从默认列表隐藏，保留消息和原始审计；“更多”中查看并恢复 |
| 知识库已删除或权限被收回 | 服务端拒绝继续检索；历史展示按当前权限策略处理，不自动改绑到其他库或默认库 |

归档操作在有活动 run 时返回冲突，待执行结束后再归档；归档不等于取消。第一版不提供永久删除会话，避免混淆现有 run 删除、审计保留与 checkpoint 清理的语义。归档会话可只读打开，恢复后才能发送。

## 4. 服务端与持久化契约

以下是拟议接口，正式实现前统一请求模型、分页上限和错误码：

| 接口 | 用途 |
|---|---|
| `POST /conversations` | 幂等创建会话，校验 scope；可使用 client_create_id 防止首次发送重复创建 |
| `GET /conversations?scope_id=...&cursor=...` | 按当前用户、范围和归档状态列出会话，按更新时间与 ID 稳定分页 |
| `GET /conversations/{id}` | 返回可访问的会话信息及 revision |
| `PATCH /conversations/{id}` | 重命名、归档或恢复；带 expected_revision，冲突时刷新后重试 |
| `GET /conversations/{id}/messages?cursor=...` | 按稳定顺序分页读取持久 turn/消息，不仅拼接最近 50 个 run |
| 会话发送入口 | 绑定 conversation_id、client_turn_id、预期会话 revision；具体采用 POST 流还是兼容当前 NDJSON，在实施前固定 |

所有读写、列表、消息、引用与 run 查询都按可信用户核对归属。请求 conversation_id 与 run 所属会话不一致时拒绝，不靠前端隐藏实现隔离。未知和无权访问的 ID 使用一致的不可访问响应。

拟增 conversation 元数据与有序 turn/message 记录；正文有明确的一份持久化权威来源，run 审计只引用相应 turn，不额外维护两份互相竞争的聊天历史。turn 至少记录请求幂等键、用户消息、已确认回答、执行状态、范围快照和关联 run。具体表结构需在 P0 核对现有 raw_conversations 与 evaluation_runs 后确定。

接受请求、写入用户 turn 和建立 initial run/control 的操作应形成一致的事务边界；回答成功后原子提交终态与已确认消息。客户端断线不丢失已接受的用户消息，也不靠页面内存判断执行是否完成。未经确认的流式片段与已完成回答区分保存和展示。

Redis checkpoint 缺失时，ContextManager 从本会话的持久记录重建有限上下文；重新生成当前系统规则、画像和技能，按当前权限校验资料。历史回答是历史表述，旧 E 编号不是本轮证据。部分失败/未完成的工具调用不能原样拼进新一轮消息。

并发约束应在多会话 MVP 就实现最小服务端保护：不同 conversation 可并行，受服务级资源额度限制；同一 conversation 只允许一个活动 turn。两个标签页同时发送时，服务端返回明确冲突或既有 run，不让两个图同时写同一 thread。client_turn_id 相同且内容相同返回已有执行；相同 ID 携带不同内容拒绝。浏览器禁用按钮不能代替此约束。

多标签页第一版通过打开/聚焦时重新读取元数据和有界状态刷新同步，不强依赖跨页实时总线。切换页面不能把迟到的流片段写入另一个会话；流事件至少携带 conversation_id、turn_id、run_id，并由对应缓冲区接收。切换是否允许继续后台接收，按当前 Streamlit 运行能力验收；做不到时提供新标签页入口或提示等待/取消，不能声称已支持后台运行。

## 5. 历史兼容和迁移

不能把旧 session 简单按最后一次知识库分组。当前旧 session 可能跨库，raw_conversations 又缺少明确库字段。

1. 先只读盘点每个用户/session 的 run 范围、时间顺序、消息关联能力和 checkpoint；输出计数及异常类型，不输出私人正文。
2. 只对可确认单一范围的旧 session 建立可重复执行的映射；保留原 session/run 标识与来源。处理空会话、重复关联和已删除库。
3. 混合范围或关联不明的旧记录进入“历史会话（旧版）”只读入口；在完成逐 turn 范围核验前不自动作为模型上下文，也不随意复制到某个库。用户可在选定范围中另开新会话。
4. 新 URL 建议为 `?conversation=<uuid>`；保留 `?session=...` 的鉴权解析与映射。遗留混合会话仍可在权限允许时查看历史，不伪装成新制会话。
5. 不直接把 UUID 拼接 user_id 写入长度可能不足的旧 thread_id 字段；先核对现有字段长度、索引、约束和兼容映射。
6. 使用新增迁移，先备份并在隔离数据库验证。迁移可重复、计数可对账；回滚保留新会话历史和映射，不能只切回旧 UI 后让新记录无法访问。

## 6. 前端布局：参考 Codex 的简洁交互

这里参考的是用户提出的产品方向，不声称复刻 Codex 内部实现。前端当前仍是 Streamlit；视觉调整和会话 API 不以迁移 React 为前提。

```text
┌─────────────────────┬────────────────────────────────────┐
│ EchoMind      收起  │ 当前会话标题              会话菜单 │
│ ＋ 新对话           ├────────────────────────────────────┤
│ 知识空间  [A ▾]     │                                    │
│ 搜索会话            │         用户问题 / 助手回答        │
│                     │         引用按需展开               │
│ 最近会话            │                                    │
│ ● 当前问题          │                                    │
│   方案比较          │                                    │
│   论文笔记          │                                    │
│                     │                                    │
│ 资料管理 ▸          ├────────────────────────────────────┤
│ 更多 ▸       设置 ⚙ │ 输入问题，/ 或 & 调用技能     发送 │
└─────────────────────┴────────────────────────────────────┘
```

- 左侧突出新对话、知识空间和会话列表；可折叠，列表支持按标题搜索。资料上传、图谱维护继续放“资料管理”；归档历史和低频功能放“更多”。
- 主区域顶部只显示会话标题和必要操作；正文以清晰间距、稳定宽度和良好表格/代码排版为主，减少装饰卡片与重复说明。
- 底部保留单一输入框、发送/停止和现有 `/`、`&` 技能入口。只在当前配置影响本次操作时显示简短提示。
- RAG、画像、长期记忆、模型服务继续集中在设置；阶段轨迹、上下文裁剪和预算信息放回答详情，不铺在首页。
- 列表提供“在新标签页打开”、重命名、归档；运行中的会话有轻量状态提示，不将完整运行轨迹塞进侧栏。
- 手机端使用抽屉式侧栏，选择后关闭；保留单主区域。键盘焦点、对比度、文字缩放、中文输入法和技能菜单必须可用。
- 延续 EchoMind 名称与品牌元素，统一边距、色彩、字体层级与图标。深浅主题可后续添加，不作为多会话上线前置条件。

应用内标签栏和双栏并排比较放第二阶段。若 Streamlit 在路由、长连接和多会话后台流方面无法满足验收，再单独评估 React 前端；迁移需独立方案，复用后端会话契约。

## 7. 与上下文计划的开发顺序

| 阶段 | 交付 | 验收门 |
|---|---|---|
| P0 共同规格 | conversation/turn/run 身份、scope 绑定、旧记录盘点、上下文重建规则、布局草图 | 不混淆显示历史与模型输入；迁移异常有明确处理 |
| P1a 会话基础 | 会话目录与持久消息、鉴权、幂等与同会话串行、范围绑定、兼容链接 | 同库两条会话独立；刷新、新标签页和过期重建可验证 |
| P1b 上下文治理 | 按主计划接入 ContextManager、证据规则和输入预算 | 实际模型输入可审计，不跨会话混入短期历史 |
| P1c 界面接入 | 简洁侧栏、会话列表/搜索/切换、重命名/归档、设置整合 | 桌面与手机可操作，技能和引用回归通过 |
| 后续增强 | 应用内标签/分屏、按需后台流、显式状态编排和耐久任务 | 先明确真实需求，分别验收，不与首版捆绑 |

P1a 的服务端契约和 P1b 的投影规则先稳定，P1c 再接入；会话持久化与基本串行保护不能推迟到可选耐久任务阶段。开发过程中如框架能力不满足设计，先记录证据、调整具体方案及验收边界。

## 8. 必测场景

1. 同一知识库新建两条会话，各自使用不同假设或约束；切换后模型输入和消息只包含本会话历史。
2. A/B 切库、默认聚合范围、直接历史链接打开，均不沿用错误的会话 ID 或工具证据。
3. 刷新、服务重启、Redis 过期后，历史仍可读取；模型上下文按策略重建，并能从 trace 验证，而不是只检查页面文字。
4. 同会话双标签发送、断线重发、相同幂等键不同内容、旧 revision 请求，均无重复执行或状态覆盖。
5. 同库不同会话同时请求能够独立推进；切换时迟到事件不写错窗口；额度按正确 run 记录。
6. 伪造他人 conversation/run/session ID、跨用户消息分页、权限收回与库删除，均不能越权读取或继续检索。
7. 单范围、混合范围、未知范围旧 session 的映射与原链接兼容；多次迁移不重复导入。
8. 搜索/分页、长标题、中文重命名、归档恢复、空会话、运行中归档冲突、手机侧栏与键盘操作通过；现有技能和引用入口保持可用。

先用隔离数据库和假模型验证，不需要为多会话验收向外部模型发送私人文档。具体真实模型验收另按已授权范围安排；实际实施与验收结果单独记录。
